# AgencyFlow 기능 요구사항 및 권한·업무 정책

> 문서 상태: 초안 v0.1 · 최종 수정일: 2026-09-27
>
> 목적: 포트폴리오 1차 구현의 기능 범위와 운영 규칙을 설명한다. (별도로 표시한 보완 항목은 완료된 기능이 아님)

## 1. 서비스 목적과 범위

AgencyFlow는 웹에이전시의 프로젝트 정보, 담당자, 일정, 이슈, 고객 소통, 자료 및 승인 이력을 프로젝트 단위로 연결하는 업무 관리 시스템이다. 역할별 대시보드에서 확인할 업무를 찾고, 상세 패널이나 관련 목록으로 이어지는 흐름을 제공한다.

| 구분 | 1차 구현 범위 |
|---|---|
| 프로젝트 | 기본 정보, 계약·고객 정보, 마일스톤, 작업상태, 담당자, 급건·이슈·당월수금 표시 |
| 업무 관리 | 대시보드, 관리 프로젝트, 처리 대기, 단계별 완료 승인·반려 |
| 일정 | 캘린더·리스트, 미완료·오늘·이번 주 일정, 변경·완료 이력 |
| 협업 | 주요 이슈사항, 소통내역, 프로젝트 자료실·첨부파일·댓글 |
| 인사 지원 | 연차 신청·승인·반려, 잔여 연차, 승인된 휴가 및 회사 휴일 |
| 운영 | 사용자·부서 관리, 로그인 잠금, 로그인·프로젝트 변경 로그 |

역할별 기본 대시보드 화면 노출은 구현되어 있으나 각 부서별 역할별 대시보드 고도화, 프로젝트 관련 알림 기능은 1차 구현 범위에 포함하지 않는다. 
후속 계획은 'Roadmap.md'를 참고한다.

## 2. 용어와 사용자 구분

| 용어 | 정의 |
|---|---|
| 마일스톤 | 화면설계, 디자인, 퍼블리싱, 프로그램 등 프로젝트의 현재 공정 |
| 작업상태 | 진행, 대기, 중지, 추가작업 등 마일스톤과 별도로 관리하는 프로젝트의 상태 |
| 일정 완료 | 개별 일정 항목의 완료 표시로 공정 승인과는 별개 |
| 단계 완료 | 담당자 완료 후 팀장과 PM이 해당 공정을 승인한 상태 |
| 프로젝트 완료 메뉴 | 현재 계정이 처리할 공정 승인 대기 목록으로 오픈·수금 완료와는 별개 |
| 단계 소요일 | 배정·시작 기준일부터 승인·종료 기준일까지의 경과일 |
| 관리 프로젝트 | 납기 지연·임박 또는 이슈 표시가 있어 확인할 프로젝트 |

저장되는 역할은 `admin`, `team_lead`, `user` 세 가지이다. 
PM 여부는 별도 역할값이 아니라 부서가 `pm`인지로 판단한다. 
팀장은 `role=team_lead` 또는 직책에 `팀장`이 포함된 사용자이다. 
PM 팀장은 PM 부서이면서 팀장 조건을 만족하는 사용자이다.

디자이너/디자인, 퍼블리셔/퍼블리싱, 프로그래머·개발·개발자/프로그램은 같은 부서로 정규화한다. 
영업과 경영관리도 별도의 업무 권한을 가지나 1차 구현 범위 내에서 부여된 권한은 제한적이다.

## 3. 권한과 화면 노출

### 3.1 주요 화면

아래 표는 현재 화면 진입·노출 기준이다. 화면이 보이는 것과 모든 항목을 수정·승인할 수 있다는 것은 다르다.

| 화면 | 관리자 | PM 팀장 | 일반 PM | 디자인·퍼블리싱·프로그램 팀장 | 해당 파트 일반 작업자 |
|---|---|---|---|---|---|
| 프로젝트 목록 | 전체 | 전체 | 전체 | 전체 | 본인 배정 프로젝트 |
| 관리 프로젝트 | 표시 | 표시 | 표시 | 표시 | 숨김 |
| 당월수금 프로젝트 | 표시 | 표시 | 표시 | 숨김 | 숨김 |
| 프로젝트 완료 | 표시 | 표시 | 표시 | 표시 | 숨김 |
| 프로젝트 배정 | 전체 담당자 관리 | PM 배정 | 숨김 | 해당 파트 배정 | 숨김 |
| 대시보드 | 전체 | 전체 | 관리 업무·일정 | 파트 관리 업무·일정 | 일정만 표시 |
| 통합데이터 | 표시 | 표시 | 숨김 | 숨김 | 숨김 |
| 프로젝트 자료실 | 표시 | 표시 | 표시 | 표시 | 표시 |
| 연차 신청·본인 내역 | 표시 | 표시 | 표시 | 표시 | 표시 |
| 연차 승인·회원·부서·로그 관리 화면 | 표시 | 숨김 | 숨김 | 숨김 | 숨김 |

- 통합데이터는 `PM 부서 AND 팀장` 조건으로 표시하며, 관리자 계정은 부서·직책 조건과 관계없이 조회할 수 있다.
- 일반 작업자는 프로젝트 완료 메뉴가 없어도 본인 담당 단계의 완료 요청을 상세 패널에서 처리할 수 있다.
- 일반 PM의 프로젝트 목록은 전체 조회이고, 일정 화면은 담당 프로젝트 기준이다. 두 범위를 혼동하지 않는다.
- 영업·경영관리 일반 사용자는 프로젝트 전체 조회가 가능하다. 영업은 프로젝트 신규 등록, 영업·경영관리는 견적서 관리 권한이 있다.

### 3.2 주요 수정 권한

| 기능 | 현재 기본 규칙 |
|---|---|
| 프로젝트 신규 등록 | 관리자, 영업 |
| 프로젝트 기본 상세 수정 | 관리자, 팀장, PM |
| 담당자 배정 | 관리자는 전체 파트, 팀장은 자기 부서 담당자 |
| 이슈 작성 | 관리자, 영업, PM, 디자인·퍼블리싱·프로그램 부서 |
| 소통내역 작성 | 관리자, 영업, PM |
| 이슈·소통내역 수정 | 관리자 외에는 작성자 기준으로 제한 |
| 이슈·소통내역 삭제 | 관리자 |
| 비공개 이슈 조회·공개범위 관리 | 관리자, 팀장, 영업, PM |
| 견적서 관리 | 관리자, 영업, 경영관리 |
| 자료실 게시글·댓글 작성 | 로그인 사용자 |
| 자료실 게시글·댓글 수정·삭제 | 관리자 |
| 회원 비밀번호 재설정·계정 활성화 | 관리자 |

이 표는 주요 업무 경로의 규칙을 요약한다. 
데이터 응답 범위와 모든 직접 API 요청을 위 표만으로 보장하는 것은 아니며, 확인해야 할 차이는 10번에 기록한다.

## 4. 기능 요구사항

| ID | 기능 | 구현 내용과 확인 기준 |
|---|---|---|
| FR-01 | 프로젝트 목록 | PJ No, 프로젝트명, 담당자, 마일스톤, 상태를 확인하고 검색·필터·정렬한다. |
| FR-02 | 프로젝트 상세 | 기본·계약·고객 정보와 링크, 일정, 이슈, 소통내역, 작업 이력을 확인한다. |
| FR-03 | 급건 표시 | 상세에서 지정한 급건 여부가 프로젝트 목록과 대시보드 배지에 반영된다. |
| FR-04 | 대시보드 요약 | 완료 승인 대기, 관리 프로젝트, 수금/오픈 체크, 미배정 프로젝트를 권한에 따라 표시한다. |
| FR-05 | 관리·처리 대기 목록 | 지연·임박·이슈 및 승인·배정·수금 확인 대상을 나누고 관련 목록으로 연결한다. |
| FR-06 | 일정 3분할 | 완료되지 않은 일정만 미완료·오늘·이번 주 남은 일정으로 구분한다. |
| FR-07 | 일정 상세 연결 | 대시보드 일정 항목을 누르면 현재 화면 위에 상세 패널을 연다. 완료 조작과 클릭 동작을 분리한다. |
| FR-08 | 통합데이터 | PM별 요약과 마일스톤 분포, 합계를 표시한다. 마일스톤 분포의 PM별 건수 클릭 시(0건 제외) 해당 PM·마일스톤 조건으로 프로젝트 목록에 이동한다. |
| FR-09 | 담당자 배정 | 파트별 선행 조건을 만족한 프로젝트에 권한이 있는 팀장이 담당자를 배정한다. 관리자는 전체 파트에 배정이 가능하다. |
| FR-10 | 공정 승인 | 담당자 → 팀장 → PM 순서로 완료·반려를 기록하고 다음 처리 대상을 표시한다. |
| FR-11 | 단계 소요일 | 담당자 이름 아래에 진행 중 또는 완료 상태의 경과일 배지를 표시한다. |
| FR-12 | 상세 검색 | 주요 이슈사항·소통내역·작업 이력을 검색한다. 일정 전체 검색 기능과 구분한다. |
| FR-13 | 자료실 | 프로젝트 연결 게시글·자료 URL·메신저 링크·첨부파일·댓글을 관리한다. 상세에서 해당 PJ No로 검색한다. |
| FR-14 | 연차·휴가 | 신청·승인·반려, 본인 잔여 연차 및 승인된 휴가 캘린더를 제공한다. |
| FR-15 | 로그인 보안 | 계정별 실패 횟수와 잠금 상태를 저장하고 관리자 비밀번호 재설정으로 해제한다. |
| FR-16 | 운영 로그 | 로그인 결과와 프로젝트 변경·공정 처리 이력을 기록한다. |

## 5. 대시보드·목록 업무 규칙

- PM 팀장은 요약 카드 4개를 표시한다. 일반 PM은 미배정 프로젝트를 숨기고 3개를 표시하며, 처리 대기에서도 담당자 배정을 숨긴다.
- 타 파트 팀장은 수금/오픈 체크를 숨기고, 관리 프로젝트·완료 승인·해당 파트 배정 업무를 확인한다.
- 일반 작업자 대시보드에는 일정만 표시한다.
- 납기일이 오늘보다 이전이면 지연, 오늘부터 14일 이내이면 임박으로 분류한다. 종료 상태인 프로젝트는 납기 경고에서 제외한다.
- 관리 프로젝트는 종료 상태가 아니면서 납기 경고 또는 `hasIssue` 표시가 있는 프로젝트이다. 이슈 메모와 이슈 체크 여부는 구분되는 데이터이다.
- 같은 프로젝트가 지연·이슈 등 여러 그룹에 포함될 수 있다. 그룹별 건수 합과 중복을 제거한 프로젝트 수는 다를 수 있다.
- 수금/오픈 체크는 당월수금 표시, 입금·오픈 관련 작업상태, 오픈 마일스톤인데 오픈일이 없는 경우 등을 대상으로 한다.
- 당월수금 목록은 monthlyCollection=true이고, 입금일이 없거나 입금일이 현재 월에 속한 프로젝트를 표시한다. 오픈일 기준은 아니다.
- 수금 완료는 입금일 존재 여부로 판단한다. 금액 요약은 목록의 잔금 합계 및 수금 완료 프로젝트의 잔금 합계이다. 회계 전표·분할 입금 관리는 포함하지 않는다.

## 6. 일정 정책

### 6.1 조회 범위

| 사용자 | 일정 화면의 표시 기준 |
|---|---|
| 관리자·PM 팀장 | 전체 프로젝트 일정 |
| 일반 PM | 본인 담당 프로젝트의 모든 일정 |
| 디자인 팀장 | 본인 등록 일정 및 화면설계·메인·서브·상세 단계 일정, 오픈 전/후 추가작업 예외 |
| 퍼블리싱 팀장 | 본인 등록 일정 및 퍼블리싱 단계 일정, 오픈 전/후 추가작업 예외 |
| 프로그램 팀장 | 본인 등록 일정 및 프로그램 단계 일정, 오픈 전/후 추가작업 예외 |
| 일반 작업자 | 본인이 등록한 일정 중심. 등록자 ID가 없는 기존 데이터는 담당자명 등으로 보완 판정 |

일정의 마일스톤이 있으면 이를 우선 사용하고, 없으면 프로젝트 마일스톤을 참조한다. 추가작업 예외는 현재 프로젝트 작업상태를 기준으로 적용한다.

### 6.2 등록·수정·완료

- PM 및 디자인·퍼블리싱·프로그램 담당자는 본인 배정 프로젝트에 일정을 등록한다. 관리자는 전체 프로젝트에 등록할 수 있다.
- PM은 일정 수정 권한을 가지며, 일반 작업자는 배정 프로젝트 안의 본인 일정만 수정한다. 팀장이라는 이유만으로 모든 일정 수정 권한을 부여하지 않는다.
- 개별 일정 완료 표시와 일정 비고 수정은 관리자·PM 권한이다. 팀장은 비고를 조회할 수 있다.
- 완료된 일정의 본문은 수정 잠금 대상으로 처리한다. 날짜·내용·완료 변경 등은 일정 이력에 남긴다.
- 미완료 일정은 오늘 이전, 오늘 확인 일정은 오늘, 이번 주 남은 일정은 내일부터 이번 주 일요일까지이다. 세 영역 모두 완료된 일정은 제외한다.
- 대시보드의 오늘은 한국 시간 기준으로 계산한다. 시스템 전체의 시간대 통일은 별도 보완 항목이다.

## 7. 담당자 배정·공정 승인·소요일

### 7.1 배정 선행 조건

| 배정 파트 | 팀장의 배정 선행 조건 |
|---|---|
| PM | 별도 선행 공정 없음 |
| 디자인 | PM이 배정되어 있음 |
| 퍼블리싱 | 디자인 단계의 담당자·팀장·PM 완료 처리 |
| 프로그램 | 퍼블리싱 단계의 담당자·팀장·PM 완료 처리 |

관리자는 전체 파트의 배정 권한을 가진다. 작업자 ID·이름과 배정 시각을 함께 관리한다.

### 7.2 공정 승인 흐름

`디자인 담당자 → 디자인 팀장 → PM → 퍼블리싱 담당자 → 퍼블리싱 팀장 → PM → 프로그램 담당자 → 프로그램 팀장 → PM`

- 담당자는 자신이 배정된 공정의 완료를 요청한다.
- 팀장은 해당 부서의 승인 단계를 처리한다.
- 일반 PM은 본인 담당 프로젝트, PM 팀장은 PM 승인 단계를 처리할 수 있다. 관리자는 전체 단계를 처리할 수 있다.
- 반려에는 사유가 필요하며, 현재 공정의 완료 상태를 되돌리고 반려 이력을 남긴다.
- 팀장이 직접 작업자로 배정되어 작업 완료하는 경우, 같은 공정의 팀장 완료까지 함께 처리하는 예외가 있다.
- 관리자에 의한 작업자 단계 처리에는 승인 목록 숨김 플래그가 적용되는 예외가 있다.
- 이 승인 흐름과 오픈일·입금일은 별도 정보이다. 프로그램 승인만으로 오픈·수금 완료를 자동 확정하지 않는다.

### 7.3 단계 소요일 계산

| 대상 | 시작 기준 | 종료 기준 |
|---|---|---|
| 디자인 | 디자인 담당자 배정일 | 디자인 PM 최종 승인일 |
| 퍼블리싱 | 퍼블리싱 담당자 배정일 | 퍼블리싱 PM 최종 승인일 |
| 프로그램 | 프로그램 담당자 배정일 | 프로그램 PM 최종 승인일 |
| PM | 프로그램 PM 최종 승인일 | 오픈일 |

- 완료 전에는 오늘을 종료일로 사용한다. 날짜 차이에 1일을 더하는 방식으로 시작일을 포함한다.
- 주말·고객 회신·승인 대기 기간도 포함하는 경과일이며 실제 투입시간이나 생산성 점수가 아니다.
- 배정일이 없으면 담당자의 가장 이른 일정 생성일/일정일, 공정 이력, 계약일 순서로 대체한다. 공정 이력의 대체 기준은 파트마다 다르다.
- PM의 프로그램 승인일이 없거나 담당자명이 없으면 해당 배지가 표시되지 않을 수 있다.
- 종료일이 없는 작업대기·중지·종료 상태는 배지를 숨긴다. 이미 완료된 배지는 유지한다. 중지 기간 자체를 차감하지 않는다.
- 완료·진행 중은 색상으로 구분하며, 배지 설명에 계산 기준을 표시한다.
- 프로젝트 목록의 상세 조건에서 `작업일정` 옵션이 선택되어 있을 때 배지를 표시한다. 해당 옵션은 기본 선택 상태이다.

## 8. 자료실·연차·로그인 운영 규칙

### 자료실

- 게시글은 프로젝트, 제목, 내용을 포함한다. 댓글은 게시글에 속한다.
- 자료실은 현재 로그인 사용자 간 공유 목록이다. 담당 프로젝트만의 비공개 자료실로 제한된 구조는 아니다.
- 게시글당 첨부파일 최대 3개, 파일당 최대 5 MiB이며 확장자·형식·크기를 검사한다. 견적서 PDF는 별도로 최대 10 MiB이다.
- 자료 URL과 메신저 URL은 HTTP/HTTPS 주소를 사용한다.
- 더미 게시글·댓글은 DB 데이터이며 코드 Push만으로 다른 환경에 복사되지 않는다.

### 연차·휴가

- 일반 사용자는 본인 연차를 신청하고, 관리자는 타 사용자 대리 등록과 승인·반려·수정·삭제를 할 수 있다.
- 상태는 대기(`pending`), 승인(`approved`), 반려(`rejected`)이다. 관리자 등록은 즉시 승인 옵션을 지원한다.
- 사용 일수는 승인 내역으로 계산하고, 승인된 휴가만 휴가 캘린더에 표시한다.
- 연차 초기 부여값은 입사일·재직기간·활성 상태·퇴사일에 따른 현재 구현 규칙으로 계산한다. 기존 연도별 잔액과 관리자 조정값도 반영한다.
- 신청 기간의 주말은 허용하지 않으며 신청 일수는 0 초과 30 이하로 검사한다.
- 위 내용은 시스템의 계산·처리 방식이며 법정 연차 산정의 모든 예외를 검증한 명세는 아니다. 실제 도입 시 회사 규정과 산정 기준을 확정해야 한다.

### 로그인·계정

- 비밀번호는 영문·숫자·특수문자를 포함한 8자 이상을 요구한다.
- 로그인 실패 횟수는 계정별로 DB에 누적한다. 5회 실패하면 해당 계정만 잠기고 해당 계정의 메모리 세션을 제거한다.
- 잠기기 전 로그인에 성공하면 실패 기록을 초기화한다. 잠긴 뒤에는 올바른 비밀번호만으로 해제되지 않는다.
- 관리자 비밀번호 재설정으로 실패·잠금 기록을 초기화한다. 서버 재시작만으로 잠금을 해제하지 않는다.
- 세션은 서버 프로세스 메모리에 저장하며 유효한 요청 때 1시간 만료 시각을 갱신한다. 서버 재시작 시 세션은 초기화된다.

## 9. 검증 범위

코드 기준 회귀 테스트는 [`tests/test_wsgi.py`](../tests/test_wsgi.py)의 14개 테스트이며, 격리된 임시 DB·비밀키를 사용한다. 로그인·잠금 해제, 역할별 데이터 조회, 배정, 승인·반려, 자료실, 저장 후 조회, WSGI 응답을 검증한다. PythonAnywhere의 실제 설정과 브라우저 화면 검증은 별도이다.

## 10. 현재 한계 및 후속 개선 계획

다음은 문서 작성 시 확인한 현 구현의 범위이며, 새로운 기능 개발을 완료 조건으로 추가하는 목록은 아니다.

| 항목 | 후속 개선 및 확인 사항 |
|---|---|
| 동시 저장 | 여러 사용자가 같은 데이터를 수정할 때 이전 변경사항이 덮어써지지 않도록 버전 기반 충돌 검사를 적용한다. |
| 역할별 대시보드 | 현재 적용된 역할별 화면 노출을 바탕으로, 디자인·퍼블리싱·프로그램 등 각 파트의 업무 특성에 맞게 대시보드를 고도화한다. 담당자는 본인의 우선 작업과 일정을, 팀장은 파트별 진행 현황과 검수·배정 대기 업무를 확인할 수 있도록 구성한다. |
| 대시보드 업무 알림 | 담당자별 배정 프로젝트의 주요 변경사항과 처리 필요 항목을 대시보드에서 알림 제공하여 대응 지연과 업무 누락을 예방한다. |
| 프로젝트 로그 | 관리자 전용 화면 정책에 맞춰 로그 조회 API도 관리자만 접근하도록 제한한다. 화면을 거치지 않는 직접 요청에서도 동일한 권한 검사가 적용되는지 확인한다. |
| 화면과 API의 권한 범위 | 메뉴·화면에서 숨겨진 기능이 직접 API 요청에서도 차단되는지 역할별 조회·수정·승인 기준을 대조한다. 일정은 화면에서 역할별로 필터링되지만 서버 응답 범위가 더 넓을 수 있어 실제 데이터 노출 범위를 확인한다. |
| PM 팀장 처리 대기 총계 | 담당자 배정 그룹이 화면에 표시되더라도 현재 처리 대기 총계에서는 배정 항목이 제외될 수 있다. 목록에 표시되는 업무 그룹과 상단 총계의 포함 기준을 일치시키거나, 프로젝트 수와 업무 건수의 차이를 명확히 표시한다. |
| 연차 예외 | 연차 이월, 공휴일, 연도 경계, 잔여일수 초과 신청 및 승인 후 변경·반려·삭제에 대한 처리 기준을 확정하고 잔여 연차와 캘린더 반영을 검증한다. |
| 자료실 조회 권한 | 일반 사용자는 본인이 배정된 프로젝트의 자료실만 조회할 수 있도록 변경한다. 게시글·댓글·첨부파일에도 동일한 접근 기준을 적용하고, 관리자·팀장의 조회 예외 범위는 별도로 정의한다. |
| 자료실 댓글 멘션·알림 | 댓글 작성 시 `@`로 해당 프로젝트 담당자를 검색·선택하여 멘션할 수 있도록 한다. 검색 결과에는 해당 프로젝트 담당자만 표시하며, 멘션된 담당자에게 알림과 해당 게시글 바로가기를 제공하여 신속한 확인과 소통을 지원한다. 댓글 등록 시에도 멘션 대상이 현재 프로젝트 담당자인지 다시 검증하며, 담당자가 아닌 사용자가 포함된 경우 안내 메시지를 표시하고 다시 선택하도록 한다.|
| 다중 프로세스 세션 | 여러 WSGI 작업 프로세스에서 로그인 상태를 일관되게 유지할 수 있도록 세션 공유 방식을 검토한다. 세션 만료·로그아웃·계정 잠금 시에도 모든 프로세스에서 동일하게 적용되는지 확인한다. |
| 시간대·기존 이력 | 데이터 저장 시간대, 화면 표시 시간대, 날짜 경계의 계산 기준을 통일한다. 기존 한국 시간·서버 현지 시각·UTC 이력의 처리 기준을 정하고, 자정 전후 일정 분류와 소요일 계산을 검증한다. |
