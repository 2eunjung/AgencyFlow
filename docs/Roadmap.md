# AgencyFlow 향후 기능 고도화 계획

> 문서 상태: 초안 v0.1 · 작성일: 2026-09-26
>
> 기준 버전: `a0ebeb0`
>
> 이 문서는 1차 구현 이후의 후보 계획이다. 기능별 확정 일정이나 구현 완료를 의미하지 않는다.

## 1. 현재 단계와 개발 방향

AgencyFlow는 프로젝트·일정·업무 이력을 통합하고, 역할별 대시보드에서 관리 대상과 처리 대기 업무를 확인하는 1차 기능을 구현했다.

현재 목표는 기능을 계속 늘리는 것이 아니라 **기존 기능을 배포·시연하고, 문제 정의와 설계 의도를 설명할 수 있는 포트폴리오로 마무리하는 것**이다. 아래 고도화는 실제 사용이나 운영 규모의 변화로 필요성이 확인될 때 진행한다.

### 구현된 범위

| 영역 | 현재 구현 |
|---|---|
| 프로젝트 관리 | 기본·계약·고객 정보, 마일스톤, 작업상태, 담당자, 급건 표시 |
| 대시보드 | 역할별 요약 카드, 지연·임박·이슈, 승인·배정·수금/오픈 확인 |
| 일정 | 미완료·오늘·이번 주 남은 일정, 캘린더·리스트, 상세 패널 연결 |
| 통합데이터 | PM별 요약·마일스톤 분포, 합계, 조건별 목록 이동 |
| 공정 관리 | 담당자 → 팀장 → PM 승인·반려, 처리 이력, 단계 소요일 |
| 자료실 | 프로젝트별 게시글, 첨부파일, 자료·메신저 URL, 댓글 |
| 연차·운영 | 신청·승인·반려, 잔액·캘린더, 회원·부서, 로그인·변경 로그 |
| 로그인·배포 코드 | 계정별 잠금, 관리자 재설정, WSGI와 로컬 API 공통 처리, 14개 통합 테스트 |

실제 배포 주소의 정상 동작, 화면별 시연 및 운영 효과 측정은 구현 완료와 구분하여 확인한다.

## 2. 포트폴리오 1차 마감

새로운 업무 기능 추가 없이 다음 항목을 확인하고 1차 버전을 마감한다.

- [ ] 실제 배포 주소에서 로그인·새로고침·저장 후 재조회 확인
- [ ] PM 팀장·일반 PM·파트 팀장·작업자 대표 계정으로 화면 노출 확인
- [ ] 일정 상세 패널, 승인·반려, 자료실 검색·댓글의 대표 동선 시연
- [ ] 체험 계정 정상 로그인 및 잠금 복구 절차 확인
- [ ] 더미 데이터와 공개 자료에 실제 고객·직원 정보가 포함되지 않았는지 확인
- [ ] README와 요구사항·DB 문서가 구현 범위와 일치하는지 확인
- [ ] 핵심 화면 캡처와 짧은 시연 영상 준비
- [ ] 1차 완료 기준점과 알려진 한계를 릴리스 설명에 기록

문서 초안에서 발견한 정책 차이는 [Requirements.md](Requirements.md)의 추가 확정 사항으로 관리한다. 운영 서비스로 전환하지 않는 한 모든 고도화 후보를 포트폴리오 마감 조건으로 확대하지 않는다.

## 3. 우선순위 기준

| 우선순위 | 진행 조건 | 목표 |
|---|---|---|
| P0 · 운영 전 | 실제 여러 사용자·실데이터 운영을 결정했을 때 | 저장 충돌, 접근 범위, 세션·복원 신뢰성 확보 |
| P1 · 업무 개선 | 기본 운영이 안정되고 반복되는 병목이 확인됐을 때 | 조치 담당자·기한, 단계 지연·승인 대기 파악 |
| P2 · 확장 | 일정·배정 이력이 축적되어 활용 근거가 생겼을 때 | 변경요청과 업무 부하 관리 |

P0는 포트폴리오에 즉시 추가할 기능 목록이 아니라 실제 운영 전 점검·개선 우선순위이다. 시연 자체가 막히거나 데이터가 손상되는 문제는 기능 확장과 관계없이 먼저 수정한다.

## 4. P0 — 실제 운영을 위한 안정성

### RM-01. 동시 수정 감지와 부분 저장

**문제:** 현재 프로젝트와 자료실은 목록·JSON 배열을 받아 재작성하는 경로가 있다. 오래된 화면에서 저장하면 먼저 저장한 사용자의 변경을 덮어쓸 수 있다.

**최소 범위:** 프로젝트·게시글별 버전 확인, 변경 항목 중심 저장, 충돌 시 최신 내용과 재확인 안내.

**완료 기준:** 두 계정이 같은 데이터를 열고 순차 저장했을 때 이전 버전의 저장이 조용히 덮어쓰지 않는다. 서로 다른 항목의 정상 변경도 보존되는지 검증한다.

### RM-02. 권한 기준과 API 응답 범위 일치

**문제:** 화면 메뉴 숨김과 서버 데이터 범위가 항상 동일한 것은 아니다. 현재 프로젝트 로그 조회와 일정 응답, 자료실 공유 범위에는 운영 정책을 확정할 부분이 있다.

**최소 범위:** 조회·수정·승인별 역할표 확정, 직접 API 접근 시 검사, 작성자·담당자·공개범위의 서버 검증. 자료실은 현재 전사 공유를 유지할지 프로젝트별로 제한할지 먼저 결정한다.

**완료 기준:** 대표 계정별로 허용 기능은 동작하고, 금지된 조회·수정은 화면을 우회한 요청에서도 거절된다. 권한표와 자동 검증의 기대 결과가 일치한다.

### RM-03. 배포·세션·백업 복원 점검

**문제:** 세션이 프로세스 메모리에 있어 재시작 시 초기화되고 여러 WSGI 작업 프로세스 간 공유되지 않는다. DB와 비밀키는 한 쌍으로 관리해야 한다.

**최소 범위:** 실제 호스팅의 프로세스 구성 확인, 필요 시 공유 세션 저장소 도입, DB·비밀키 백업과 격리 환경 복원 절차, 체험 계정 잠금 복구 절차.

**완료 기준:** 운영 구성에서 로그인 상태가 예상대로 유지된다. 복원한 별도 환경에서 로그인·프로젝트·자료실·첨부파일을 확인하고, 절차와 복원 결과를 기록한다.

## 5. P1 — 처리 업무의 후속 조치와 병목 관리

### RM-04. 이슈 후속 조치

**문제:** 이슈 내용이 있어도 누가 언제까지 해결할지 분명하지 않으면 같은 확인이 반복된다.

**최소 범위:** 조치 담당자, 처리 목표일, 다음 행동, 해결 상태. 기존 프로젝트 이슈 기록에서 확장한다.

**예시:** 고객 상품 이미지 미수급 → 담당 PM 지정 → 요청 기한 등록 → 회신 확인 후 해결 처리.

**완료 기준:** 미해결 이슈의 담당자와 기한을 조회하고, 기한 초과 항목을 구분하며, 해결 후 후속 조치 목록에서 제외한다.

### RM-05. 단계별 목표일과 납기 변경 이력

**문제:** 최종 납기일까지 남은 일수만으로는 현재 공정의 지연을 일찍 파악하기 어렵다.

**최소 범위:** 주요 공정 목표일, 현재 공정의 지연 표시, 고객 자료·회신 대기 사유, 최초 납기와 변경 납기·사유·합의 기록.

**완료 기준:** 단계 목표일 초과를 확인할 수 있고, 납기를 변경해도 최초 약속일과 변경 이력이 남는다.

### RM-06. 작업 구간과 승인 대기 구간 구분

**문제:** 현재 단계 소요일에는 실제 작업, 고객 회신, 팀장·PM 승인 대기가 함께 포함된다. 이 숫자만으로 담당자의 작업량을 평가하기 어렵다.

**최소 범위:** 담당자 완료·팀장 승인·PM 승인 시각을 기준으로 각 구간 분리. 중지·재개, 반려·재작업, 담당자 변경의 집계 기준을 먼저 확정한다.

**완료 기준:** 현재 경과일 배지와 구간별 시간이 구분되며, 이력이 없는 기존 데이터는 확정값처럼 표시하지 않는다. 경과일과 투입 공수를 같은 지표로 표현하지 않는다.

## 6. P2 — 범위·비용·인력 판단 지원

### RM-07. 변경요청 관리

**문제:** 오픈 전/후 추가작업 상태만으로는 계약 범위, 추가 일정·비용, 고객 합의 여부를 추적하기 어렵다.

**최소 범위:** 요청 내용·요청일, 계약 범위 포함 여부, 예상 일정·비용 영향, 내부 승인자, 고객 확인 기록, 관련 자료 연결.

**완료 기준:** 추가 요청이 검토·승인·진행 중 어느 상태인지 확인하고, 프로젝트별 승인된 범위와 일정 변경 근거를 찾아볼 수 있다.

### RM-08. 작업자·PM별 리소스 현황

**문제:** 프로젝트 건수만으로는 규모·난이도·가까운 납기·휴가를 반영한 업무 부하를 판단하기 어렵다.

**최소 범위:** 담당자별 진행 업무, 가까운 일정, 승인 대기, 휴가 표시. 난이도·예상 작업량은 입력 기준과 유지 가능성을 확인한 후 도입한다.

**완료 기준:** 팀장이 배정 화면에서 특정 기간의 집중 일정과 부재를 확인한다. 근거 없는 자동 점수나 추천을 초기 범위에 포함하지 않는다.

### RM-09. 급건 사유와 우선순위 조정 기록

**문제:** 급건 배지가 여러 프로젝트에 붙으면 우선순위 결정 이유와 기존 일정에 미친 영향을 설명하기 어렵다.

**최소 범위:** 급건 사유, 요청 완료 시점, 결정자, 급건 종료 여부, 영향을 받는 기존 일정 연결.

**완료 기준:** 급건 지정 이유와 종료 이력을 확인하고, 일정 조정이 발생한 프로젝트에서 그 근거를 추적한다.

## 7. 진행 순서와 범위 관리

`1차 포트폴리오 마감 → 운영 필요성 확인 → 권한·저장·배포 안정성 → 이슈 후속 조치 → 단계 일정·대기 분석 → 변경요청·리소스 관리`

- 한 번에 하나의 업무 문제를 선택하고 최소 범위를 먼저 구현한다.
- 시작 전에 적용 사용자, 필요한 데이터, 완료 기준, 제외 범위를 기록한다.
- 필요한 입력이 계속 유지될 수 있는지 확인한다. 데이터가 없는 지표는 먼저 수집 기준을 마련한다.
- 기존 일정·승인·자료실 기능에 대한 회귀 검증을 유지한다.
- 완료 기준을 충족하면 버전을 마감하고 새 아이디어는 별도 후보로 이동한다.
- 외부 메신저 알림, 고객 포털, AI 요약 등은 사용 필요성과 운영 비용을 확인하기 전까지 보류한다.

## 8. 효과 검증 계획

아래는 향후 측정 후보이며 이미 달성한 성과 수치가 아니다. 현재 코드가 모든 지표를 자동 수집하는 것도 아니다.

| 확인할 효과 | 측정 방법 후보 |
|---|---|
| 필요한 업무를 빨리 찾는가 | 대표 과업에서 대시보드 진입부터 대상 상세 확인까지 시간·이동 횟수 비교 |
| 승인 병목을 줄이는가 | 담당자 완료 → 팀장 승인 → PM 승인 구간의 대기일 추이 |
| 이슈가 방치되지 않는가 | 담당자·기한이 없는 미해결 이슈와 기한 초과 건수 |
| 저장 결과를 신뢰할 수 있는가 | 충돌 감지·해결 사례, 저장 후 누락 제보 기록 |
| 입력 부담이 적절한가 | 사용자 피드백, 필수 필드 누락, 중복 입력 사례 |

실제 팀 적용 후 기준 기간과 측정 방법을 정하고, 결과를 확인한 뒤 포트폴리오의 운영 성과에 반영한다.
