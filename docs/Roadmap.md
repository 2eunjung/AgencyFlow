# AgencyFlow 향후 기능 고도화 계획

> 문서 버전: v1.0 · 최종 수정일: 2026-09-28
>
> 구현 확인 기준: `a0ebeb0`
>
> 이 문서는 1차 구현 이후의 개선 계획을 정리한 문서이다. 각 항목은 향후 개발 후보이며, 현재 구현 완료를 의미하지 않는다.

## 1. 현재 단계와 개발 방향

AgencyFlow는 프로젝트·일정·업무 이력을 통합하고, 역할별 대시보드에서 관리 대상과 처리 대기 업무를 확인하는 1차 기능을 구현했다.

현재 목표는 새로운 기능을 계속 추가하는 것보다 기존 기능을 안정적으로 배포하고, 문제 정의와 설계 의도를 설명할 수 있는 포트폴리오로 마무리하는 것이다.

아래 고도화 계획은 실제 사용자와 실데이터를 이용한 운영 필요성이 확인될 때 단계적으로 진행한다. 시연을 막거나 데이터 손실로 이어지는 문제는 우선 처리하되, 모든 고도화 항목을 포트폴리오 1차 완료 조건으로 포함하지 않는다.

### 현재 구현 범위

| 영역 | 현재 구현 |
|---|---|
| 프로젝트 관리 | 기본·계약·고객 정보, 마일스톤, 작업상태, 담당자, 급건 표시 |
| 대시보드 | 권한별 요약 카드, 지연·임박·이슈, 승인·배정·수금/오픈 확인 |
| 일정 | 미완료·오늘·이번 주 남은 일정, 캘린더·리스트, 상세 패널 연결 |
| 통합데이터 | PM별 요약·마일스톤 분포, 합계, 조건별 프로젝트 목록 이동 |
| 공정 관리 | 담당자 → 팀장 → PM 승인·반려, 처리 이력, 단계 소요일 |
| 자료실 | 프로젝트별 게시글, 첨부파일, 자료·메신저 URL, 댓글 |
| 연차·운영 | 신청·승인·반려, 잔여 연차·휴가 캘린더, 회원·부서 관리 |
| 로그인·로그 | 계정별 로그인 잠금, 관리자 재설정, 로그인·프로젝트 변경 로그 |
| 배포 코드 | WSGI와 로컬 API의 공통 처리 및 14개 회귀 테스트 |

실제 배포 환경의 정상 동작, 사용자별 화면 검증 및 운영 효과 측정은 기능 구현과 별도로 확인한다.

## 2. 우선순위 기준

| 우선순위 | 진행 조건 | 목표 |
|---|---|---|
| **P0 · 운영 전** | 여러 사용자와 실데이터를 이용한 운영을 결정했을 때 | 저장 충돌, 권한, 집계, 세션, 시간대, 연차 정책의 신뢰성 확보 |
| **P1 · 업무 개선** | 기본 운영이 안정되고 반복되는 누락·병목이 확인됐을 때 | 역할별 우선 업무, 알림, 협업 및 단계 지연 파악 |
| **P2 · 운영 확장** | 일정·배정·변경 이력이 충분히 축적됐을 때 | 변경요청과 리소스·우선순위 관리 |

P0는 포트폴리오에 즉시 추가할 기능 목록이 아니라 실제 운영 전 점검할 우선순위이다.

## 3. P0 — 실제 운영을 위한 안정성

### RM-01. 동시 수정 감지와 부분 저장

**문제:** 현재 프로젝트는 전달받은 목록을 기존 데이터와 병합해 저장하고, 자료실은 개별 게시글·댓글 요청을 처리하면서 전체 게시글 배열을 다시 저장한다. 변경 버전을 비교하는 검사가 없어, 여러 사용자가 같은 데이터를 수정할 때 이전 변경사항이 덮어써질 수 있다.

**최소 범위**

- 프로젝트·게시글별 버전 기반 충돌 검사
- 전체 목록이나 배열을 다시 저장하는 경로를 변경 항목 중심의 저장 방식으로 개선
- 충돌 발생 시 최신 데이터와 다시 확인할 항목 안내
- 서로 다른 항목을 수정한 경우 변경사항이 누락되지 않고 저장되는지 검증

**완료 기준:** 두 계정이 같은 데이터를 열고 순차적으로 저장했을 때 이전 변경사항이 안내 없이 사라지지 않는다. 서로 다른 항목을 수정한 경우에는 각 변경사항이 유지된다.

### RM-02. 권한·조회 범위 및 처리 대기 집계 기준 정합성

**문제:** 화면의 메뉴 노출 조건과 서버의 데이터 조회 범위가 항상 일치하는 것은 아니다. 화면을 거치지 않은 직접 요청에서도 동일한 권한 검사가 적용되어야 한다.

또한 PM 팀장에게 담당자 배정 그룹이 표시되지만 현재 처리 대기 총계에서는 배정 항목이 제외된다. 총계는 중복을 제거한 프로젝트 수로 계산하므로, 포함 대상과 표시 단위를 명확히 정해야 한다.

**최소 범위 — 권한과 조회 범위**

- 프로젝트 로그 조회 API를 관리자 권한으로 제한
- 일정 데이터 응답을 사용자 역할과 담당 프로젝트 범위에 맞게 제한
- 일반 사용자는 본인에게 배정된 프로젝트의 자료실만 조회하도록 제한
- 자료실 게시글·댓글·첨부파일에 동일한 접근 기준 적용
- 관리자·팀장의 자료실 조회 예외 범위 확정
- 배정 해제 후 기존 자료실 접근 및 작성글 관리 기준 확정
- 관리자 계정은 부서·직책과 관계없이 통합데이터를 조회할 수 있도록 권한 검사 보완

**최소 범위 — 처리 대기 집계**

- PM 팀장의 처리 대기 총계에 포함할 업무 그룹 확정
- 담당자 배정 목록의 노출 조건과 총계 반영 기준 일치
- 총계가 중복을 제거한 프로젝트 수인지 업무 건수인지 화면에 명확히 표시
- 동일 프로젝트가 여러 업무 그룹에 포함되는 경우의 집계 검증

**완료 기준:** 대표 계정별 허용 기능은 정상적으로 동작하고, 허용되지 않은 조회·수정은 직접 API 요청에서도 거절된다. 문서의 권한 기준, 화면 노출 및 자동 검증 결과가 일치한다.

PM 팀장의 처리 대기 총계는 확정한 업무 그룹을 포함하며, 동일 프로젝트의 중복 집계 여부와 표시 단위가 화면 설명과 일치한다.

### RM-03. 배포·세션·백업·시간 기준 점검

**문제:** 로그인 세션이 서버 프로세스 메모리에 저장되어 재시작 시 초기화되고, 여러 WSGI 작업 프로세스 사이에서 자동으로 공유되지 않는다. 브라우저 한국 날짜, 서버 현지 시각, UTC 문자열도 함께 사용하고 있다.

**최소 범위**

- 실제 호스팅 환경의 WSGI 작업 프로세스 구성 확인
- 필요 시 DB 또는 별도 저장소를 이용한 공유 세션 도입
- 세션 만료·로그아웃·계정 잠금의 프로세스 간 일관성 검증
- DB와 비밀키의 백업·복원 절차 작성
- 분리된 환경에서 백업 데이터 복원 검증
- 데이터 저장 시각과 화면 표시 시간대 기준 확정
- 기존 한국 시간·서버 현지 시각·UTC 이력의 처리 원칙 정의
- 자정 전후 일정 분류와 단계 소요일 계산 검증

**완료 기준:** 실제 운영 구성에서 로그인 상태와 계정 잠금이 일관되게 유지된다. 백업 복원 후 로그인·프로젝트·자료실·첨부파일을 확인할 수 있으며, 날짜와 시각이 정해진 기준으로 표시된다.

### RM-04. 연차 예외 정책 검증

**문제:** 현재 연차 기능은 기본적인 신청·승인·반려·잔여 일수 계산과 변경·삭제 후 재계산을 지원한다. 다만 회사별 운영 규정과 연도 경계에 따른 예외 기준은 추가로 확정하고 검증해야 한다.

**최소 범위**

- 미사용 연차 이월 여부와 이월 한도
- 회사 휴일과 공휴일의 신청 일수 반영 기준
- 두 연도에 걸친 연차 신청 처리 방식
- 잔여 일수를 초과한 신청의 허용·차단 기준
- 승인 후 일정 변경·반려·삭제 및 연도 변경 시 기존 잔여 일수 재계산의 일관성 검증
- 퇴사 예정자와 관리자 조정값의 처리 기준

**완료 기준:** 주요 예외 상황별 예상 결과를 문서화하고, 신청 내역·잔여 일수·휴가 캘린더가 같은 기준으로 반영된다.

## 4. P1 — 역할별 업무 확인과 협업 개선

### RM-05. 역할별 대시보드 고도화와 업무 알림

**문제:** 현재 역할에 따라 대시보드 화면이 구분되고 일정·배정·승인 대기·수금/오픈 확인 항목을 제공하지만, 각 부서와 직책에서 먼저 확인해야 할 업무와 새로 발생한 변경사항을 충분히 안내하지는 않는다.

기존 일정과 처리 대기 목록을 기반으로 파트별 우선순위와 진행 현황을 보강하고, 새로운 변경사항을 전달하는 앱 내부 알림을 추가한다.

**최소 범위 — 기존 대시보드 보완**

- 디자인·퍼블리싱·프로그램 담당자의 일정과 작업을 우선순위에 따라 정리
- 파트 팀장의 기존 배정·승인 대기 목록에 검수 우선순위와 파트 진행 현황 보강
- PM의 기존 이슈·일정·수금/오픈 확인 항목을 담당 프로젝트의 우선순위에 맞게 정리

**최소 범위 — 앱 내부 알림 추가**

- 일정 도래, 승인 대기, 담당자 배정, 주요 이슈 변경을 알림으로 제공
- 알림 읽음 여부와 확인 시각 관리
- 알림에서 관련 프로젝트·일정·승인 화면으로 바로 이동
- 중복 알림과 완료된 업무의 알림 종료 기준 정의

**완료 기준:** 사용자가 로그인 후 자신의 우선 업무와 새로 발생한 확인 항목을 대시보드에서 파악하고 관련 화면으로 이동할 수 있다.

### RM-06. 자료실 댓글 멘션과 앱 내부 알림

**문제:** 자료실 댓글을 작성해도 확인이 필요한 담당자를 지정하거나 댓글 등록 사실을 직접 전달할 방법이 없다.

**최소 범위**

- 댓글에서 `@`로 해당 프로젝트 담당자 검색·선택
- 검색 결과를 프로젝트 담당자로 제한
- 댓글 등록 시 멘션 대상이 현재 담당자인지 서버에서 재검증
- 담당자가 아닌 사용자가 포함된 경우 안내 후 재선택
- 멘션된 담당자에게 앱 내부 알림 제공
- 알림에서 해당 자료실 게시글로 바로 이동
- 알림 읽음 처리와 댓글 수정 시 재알림 기준 정의

**완료 기준:** 프로젝트 담당자만 유효한 멘션 대상으로 등록되고, 멘션된 사용자가 알림을 통해 해당 댓글을 확인할 수 있다.

이 단계의 알림은 AgencyFlow 내부 알림을 의미한다. 이메일·Slack·카카오톡 등 외부 서비스 연동은 운영 필요성과 유지 비용을 확인한 후 별도로 검토한다.

### RM-07. 이슈 후속 조치 관리

**문제:** 현재 이슈 내용과 상태·해결 여부를 관리할 수 있지만, 누가 언제까지 어떤 조치를 해야 하는지는 별도로 관리하지 않는다. 이로 인해 동일한 확인이 반복되거나 처리 시점을 놓칠 수 있다.

**최소 범위**

- 조치 담당자
- 처리 목표일
- 다음 행동
- 기존 이슈 상태·해결 여부와 후속 조치의 완료 기준 연결
- 관련 자료와 소통내역 연결
- 기한 초과 및 담당자·기한 미지정 항목 구분

**예시:** 고객 상품 이미지 미수급 → 담당 PM 지정 → 요청 기한 등록 → 회신 확인 후 해결 처리

**완료 기준:** 미해결 이슈의 담당자와 기한을 조회할 수 있고, 기한이 지난 항목을 구분하며, 해결된 항목은 후속 조치 목록에서 제외된다.

### RM-08. 단계별 목표일과 납기 변경 이력

**문제:** 최종 납기일까지 남은 기간만으로는 현재 작업 단계의 지연을 일찍 파악하기 어렵다. 기존 일정과 변경 이력을 바탕으로, 공정별 목표일과 프로젝트 납기 변경의 근거를 구분해 관리할 필요가 있다.

**최소 범위**

- 주요 공정별 목표일
- 현재 공정의 지연 표시
- 고객 자료·회신 대기 사유
- 최초 납기와 변경 납기
- 납기 변경 사유·결정자·고객 합의 기록

**완료 기준:** 단계 목표일을 초과한 프로젝트를 확인할 수 있고, 납기를 변경해도 최초 약속일과 변경 근거가 유지된다.

## 5. P2 — 범위·비용·인력 판단 지원

### RM-09. 변경요청 관리

**문제:** 오픈 전·후 추가작업 상태만으로는 계약 범위, 추가 일정·비용 및 고객 합의 여부를 추적하기 어렵다.

**최소 범위**

- 요청 내용과 요청일
- 계약 범위 포함 여부
- 예상 일정·비용·작업 공수
- 내부 검토·승인자
- 고객 확인 기록
- 관련 일정·소통·자료 연결
- 검토·승인·진행·완료 상태

**완료 기준:** 추가 요청의 비용 입금 여부 및 처리 상태를 확인하고, 프로젝트별 승인 범위와 일정·비용 변경 근거를 조회할 수 있다.

### RM-10. 작업자·PM별 리소스 현황

**문제:** 담당 프로젝트 건수만으로는 프로젝트 규모·난이도·납기 집중도·휴가를 반영한 업무 부하를 판단하기 어렵다.

**최소 범위**

- 담당자별 진행 프로젝트와 작업 단계
- 가까운 일정과 승인 대기
- 휴가와 부재 일정
- 같은 기간에 집중된 납기
- 필요성이 확인된 경우 예상 작업량과 난이도 입력

**완료 기준:** 팀장이 담당자를 배정할 때 특정 기간의 일정 집중도와 부재 여부를 함께 확인할 수 있다. 입력 근거가 없는 자동 점수나 추천은 초기 범위에 포함하지 않는다.

### RM-11. 급건 사유와 우선순위 조정 기록

**문제:** 여러 프로젝트에 급건 배지가 표시되면 어떤 업무를 먼저 처리해야 하는지, 기존 일정에 어떤 영향을 주었는지 설명하기 어렵다.

**최소 범위**

- 급건 지정 사유
- 요청 완료 시점
- 요청자와 우선순위 결정자
- 급건 지정·해제 이력
- 급건으로 인해 조정된 기존 일정 연결

**완료 기준:** 급건 지정 이유와 종료 이력을 확인할 수 있고, 일정 변경이 발생한 프로젝트에서 조정 근거를 추적할 수 있다.

## 6. 진행 순서와 범위 관리

`포트폴리오 1차 마감 → 운영 필요성 확인 → 저장·권한·집계·세션·시간대·연차 정책 안정화 → 역할별 알림·협업 개선 → 이슈·단계 지연 관리 → 변경요청·리소스·급건 관리`

- 한 번에 하나의 업무 문제를 선택하고 최소 범위를 먼저 구현한다.
- 시작 전에 적용 사용자, 필요한 데이터, 완료 기준과 제외 범위를 기록한다.
- 새로운 기능에 필요한 데이터가 지속적으로 입력될 수 있는지 확인한다.
- 데이터가 없는 지표는 먼저 수집 기준을 마련한다.
- 기존 일정·승인·자료실·연차 기능에 대한 회귀 검증을 유지한다.
- 완료 기준을 충족하면 해당 버전을 마감하고 새 아이디어는 별도 후보로 이동한다.
- 고객 포털, AI 요약 및 외부 메신저 알림은 사용 필요성과 운영 비용을 확인하기 전까지 보류한다.
